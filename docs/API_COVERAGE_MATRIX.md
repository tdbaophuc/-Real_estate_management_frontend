## Refactor Order

1. Auth + shared API client + Files + Master Data: this stabilizes tokens, upload/download, locations, amenities, listing packages, and form dependencies.
2. Properties + Listings + Public Search: these are central asset/listing flows and have several Stitch screens plus route gaps (`/listings/:id`).
3. Customers + Leads + Follow-up Tasks + AI customer/lead helpers: this enables CRM detail, Trello-style pipeline, task lifecycle, and AI insights.
4. Appointments: calendar/list/detail lifecycle requires correct time filters and status mutations.
5. Contracts + Transactions + Commissions: financial/legal workflows should come after property/listing/customer context is reliable.
6. Dashboard + Reports + Notifications: polish data summaries after transactional domains are stable.
7. Admin Users + Audit Logs + remaining AI assistant coverage: finish governance and cross-cutting observability.

## Key Risks

- Heuristic wrapper matching can miss equivalent code paths or mark a wrapper as covered even when DTO payload differs from backend. Domain refactor must still inspect request/response types manually.
- Some current routes exist without dedicated detail/create routes required by the Stitch plan, notably listing detail workflow, and possibly contract/transaction create/edit flows.
- Shared services such as Files and Master Data have no standalone route by design; completion depends on every consuming form/component using them consistently.
- API reference marks some admin endpoints as public, but frontend should still enforce role guards until backend security is verified.
- Build passes, but the large production bundle warning indicates future code splitting is needed as screens become richer.
- Stitch is a visual target, not an API contract. Generated screens may not map exactly to backend capabilities, so API truth should drive behavior while Stitch drives workspace structure and visual density.
